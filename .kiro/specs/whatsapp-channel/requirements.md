# Requirements Document

## Introduction

whatsapp-channel sends an owner-approved WhatsApp draft to the buyer together with a Razorpay test-mode payment link, and marks the invoice paid when Razorpay reports the link as paid, so the tombstone resurrects. It is the third link of the demo spine: escalation draft approved by the owner → **WhatsApp nudge with a Razorpay test link lands on a phone** → … → test payment → **the tombstone resurrects**.

Meta WhatsApp Cloud API is out of scope. Our Meta accounts are locked (error 131031, new unverified business portfolio, 18 Nov). Meta Cloud API stays on the roadmap until business verification. This overrides the "WhatsApp Cloud API (test number)" line in `tech.md`.

Every sender sits behind one Message_Channel interface:
- primary: the Twilio_Sandbox, which sends a free-form message inside the 24-hour window the buyer opens by sending `join <code>`, and only to numbers that joined the sandbox;
- backup: a WaMe_Link (message prefilled; the owner taps Send on their own phone), shown next to the send button.

The spec is lean, and it adds no legal or money maths outside `packages/engine`. The send-time check calls the Engine `nextEscalationStep`. Every amount is integer paise formatted with the Engine `formatINR`. The message text is the Draft text the owner approved; the only additions are the payment link line and the existing Basis_Line and Disclaimer. Nothing is sent unless the owner clicks a send control on an approved Draft.

Tests are mandatory in this spec. No test task may be marked optional. The one manual live check (Requirement 9 criterion 9) is a manual step outside the test suite, and it is not a test task.

Non-goals: Meta Cloud API; WhatsApp message templates; voice (buyer-voice-call); tracking Twilio delivery status (status callbacks); replying to or acting on inbound messages; partial payments, refunds and link expiry handling; editing buyer details in the UI; the "Start call" button (stays disabled).

## Glossary

- **Engine**, **Decision**, **Ladder_Step**, **Session_Supplier**, **Stale_Session**, **Draft**, **Drafts_Table**, **Escalation_Event**, **Approved_Step_Event**, **Engine_History**, **Body_Text**, **Basis_Line**, **Final_Text**, **Fact_Sheet**, **Disclaimer**, **Tool_Log**, **Approval_Queue**, **Demo_Seed**, **Ladder_Runner**, **Model_Output**: as defined in `.kiro/specs/escalation-ladder/requirements.md`.
- **Debtor_Page**, **Invoice_Panel**, **Today**, **Candle_Timeline**, **Action_Text**, **Placeholder_Buttons**, **Buyer_Id**: as defined in `.kiro/specs/debtor-ui/requirements.md`.
- **Demo_Override**, **Tombstone_State**, **Graveyard_Page**, **Wait_Text**, **Step_Text**: as defined in `.kiro/specs/dashboard-ui/requirements.md`.
- **Message_Channel**: the one TypeScript interface in `packages/agent` that every WhatsApp sender implements. It takes a recipient number, the Outbound_Text and an idempotency key, and returns either a sent result (provider message id), a handoff result (a URL the owner opens) or a failure (error kind and provider error code).
- **Twilio_Sandbox**: the Message_Channel implementation that posts to the Twilio Messages API from the Twilio WhatsApp Sandbox number.
- **WaMe_Link**: the Message_Channel implementation that makes no network call and returns `https://wa.me/<digits>?text=<URL-encoded Outbound_Text>`, where `<digits>` is the Buyer_Number without `+`.
- **Buyer_Number**: the new nullable `buyers.whatsapp_number` column, an E.164 number matching `^\+[1-9][0-9]{7,14}$`.
- **Sendable_Draft**: a Draft with status `approved`, step `whatsapp_nudge` or `whatsapp_paylink`, belonging to an invoice of the Session_Supplier, with no Sent_Message.
- **Approval_Day**: the `occurred_on` of the Approved_Step_Event of a Draft.
- **Send_Check**: the Engine call `nextEscalationStep(invoice, history, Today, default LadderConfig)`, where `history` is the Engine_History of the invoice without the Approved_Step_Event of the Draft being sent. The Send_Check passes when the Decision is `advance` with the Draft's step, which is the same test the Approval_Queue applies at approval time.
- **Pay_Amount**: the invoice principal `amount_paise`, in integer paise.
- **Pay_Link**: a Razorpay test-mode Payment Link created for one Sendable_Draft, stored as one `payment_links` row.
- **Pay_Link_Line**: the line `Pay <formatINR(Pay_Amount)> here: <Pay_Link URL>`.
- **Pay_Link_Marker**: the fixed text `[payment link added on send]` that escalation-ladder places in `whatsapp_paylink` Drafts.
- **Outbound_Text**: the text sent to the buyer, built from the Draft: the Draft's `body_text` with the Pay_Link_Marker replaced by the Pay_Link URL only, so that the sentence around the marker still reads as a sentence (or, only when the body has no Pay_Link_Marker, the body followed by a blank line and the Pay_Link_Line), then a blank line, the Basis_Line built from the Draft's `rule_ids`, a line break and the Disclaimer as the last line. It is built with the escalation-ladder Final_Text builder.
- **Message_Row**: one row of the existing `messages` table, which this spec extends with `draft_id` (nullable, references `drafts.id` on delete restrict), `provider_message_id` (nullable text) and `error_code` (nullable text), plus a partial unique index on `messages.draft_id` WHERE `status` IN (`'sent'`, `'handed_off'`), all through a Drizzle migration (Requirement 5 criterion 8).
- **Sent_Message**: an outbound Message_Row of a Draft whose status is `sent` or `handed_off`.
- **Razorpay_Webhook**: the HTTP route `POST /api/webhooks/razorpay` in `apps/web`.
- **Twilio_Webhook**: the HTTP route `POST /api/webhooks/twilio` in `apps/web`.
- **Webhook_Event_Table**: the new table `webhook_events` (`id` uuid primary key, `provider` text, `event_id` text, `received_at` timestamptz), with a unique constraint on (`provider`, `event_id`).
- **Channel_Env**: the env vars `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_WHATSAPP_FROM`, `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` and `PUBLIC_BASE_URL`, plus the optional `TWILIO_SANDBOX_JOIN_CODE` and `DEMO_BUYER_WHATSAPP`. `TWILIO_WHATSAPP_FROM` is an E.164 number without the `whatsapp:` prefix and must match `^\+[1-9][0-9]{7,14}$`; any other value is treated as unset (Requirement 8 criterion 4). `TWILIO_SANDBOX_JOIN_CODE` holds the code only, without the word `join`; messages render it as `join <code>`. `PUBLIC_BASE_URL` is the production domain, never a Vercel preview URL.
- **Payment_Day**: the date stored as `invoices.paid_on` when a Pay_Link is paid: for the demo supplier, the `created_on` of the Pay_Link (the Today in effect when it was sent); for every other supplier, the Asia/Kolkata calendar date of `payload.payment.entity.created_at` (Unix seconds) in the `payment_link.paid` event.
- **Razorpay_Link_Lookup**: the Razorpay API call `GET /v1/payment_links?reference_id=<Draft id>`, which returns any Payment Link already created with that Draft id as its `reference_id`.

## Requirements

### Requirement 1: Message_Channel and buyer number

**User Story:** As a developer, I want every WhatsApp sender behind one interface, so that Meta Cloud API can replace the Twilio sandbox later without touching callers.

#### Acceptance Criteria

1. THE `packages/agent` package SHALL export one Message_Channel interface with exactly two implementations in this spec, Twilio_Sandbox and WaMe_Link, and no `apps/web` module SHALL call the Twilio API or build a wa.me URL except through a Message_Channel implementation.
2. WHEN the send server actions call the Twilio_Sandbox with a Buyer_Number and an Outbound_Text, THE Twilio_Sandbox SHALL make exactly one Twilio Messages API call that sends the Outbound_Text unchanged as a free-form WhatsApp message from `whatsapp:<TWILIO_WHATSAPP_FROM>` to `whatsapp:<Buyer_Number>`, SHALL make no automatic retry, and, when Twilio accepts the message, SHALL return a sent result that holds the Twilio message SID as the provider message id.
3. IF the Twilio API rejects a send with error 63015 (the number has not joined the sandbox) or error 63016 (the 24-hour window is closed), or a status poll of criterion 7 reports status `failed` or `undelivered` with error code 63015 or 63016, THEN THE Twilio_Sandbox SHALL return a failure that holds that error code, THE Debtor_Page SHALL show "This number hasn't joined the WhatsApp sandbox in the last 3 days, or its 24-hour window has closed. Ask the buyer to send join <TWILIO_SANDBOX_JOIN_CODE> to the sandbox number, or use Open in WhatsApp." with `role="alert"`, and "Open in WhatsApp" SHALL stay available. WHERE `TWILIO_SANDBOX_JOIN_CODE` is unset or empty, the message SHALL read "send the join code from the Twilio sandbox page" in place of "send join <TWILIO_SANDBOX_JOIN_CODE>", with no literal placeholder and no empty join command.
4. WHEN the send server actions call the WaMe_Link with a Buyer_Number and an Outbound_Text, THE WaMe_Link SHALL return a handoff result whose URL is exactly `https://wa.me/<digits>?text=<URL-encoded Outbound_Text>`, where the text is percent-encoded as UTF-8 so that line breaks, `₹` and Hinglish characters survive a round trip unchanged, and THE WaMe_Link SHALL make no network call.
5. THE `packages/db` schema SHALL add the nullable Buyer_Number column to `buyers` through a Drizzle migration, with a check constraint for `^\+[1-9][0-9]{7,14}$`, so that the database rejects an insert or update with a non-matching value and existing `buyers` rows keep a null Buyer_Number after the migration.
6. WHERE `DEMO_BUYER_WHATSAPP` is set to a value matching `^\+[1-9][0-9]{7,14}$`, THE Demo_Seed SHALL store it as the Buyer_Number of Sharma Traders; IF `DEMO_BUYER_WHATSAPP` is unset, empty or does not match that pattern, THEN THE Demo_Seed SHALL leave every Buyer_Number null, finish seeding without error, and print a warning that names the variable without printing its value. Phone numbers in the repository are governed by Requirement 8 criterion 3.
7. THE Twilio_Sandbox SHALL time out the create call after 10 seconds. WHEN Twilio accepts the message (HTTP 2xx with a message SID), THE Twilio_Sandbox SHALL fetch the message status (`GET /2010-04-01/Accounts/{AccountSid}/Messages/{MessageSid}.json`, same Basic auth) up to 3 times, 2 seconds apart, with each poll capped at 1 second, and stop at the first `failed` or `undelivered` status; a poll that errors, times out or returns a non-2xx response SHALL end polling with a sent result, as SHALL statuses still `queued`, `sent`, `delivered` or `read` after the last poll. IF the Twilio API returns any error other than 63015 or 63016 on the create call, or the create call gets no response within 10 seconds, or the create request fails at the network level (in each of these three cases with no status poll), or a poll reports `failed` or `undelivered` with any other error code (or none), THEN THE Twilio_Sandbox SHALL return a failure that holds the error kind and the Twilio error code (empty when Twilio returned none), SHALL NOT throw an error to its caller, and THE Debtor_Page SHALL show a `role="alert"` error saying the message was not sent, with "Open in WhatsApp" still available.

### Requirement 2: Send only an approved Draft, after re-checking the Engine

**User Story:** As a supplier, I want only messages I approved to reach my buyer, and never after the buyer has promised or paid, so that the relationship is protected.

#### Acceptance Criteria

1. THE send server actions SHALL read only a Draft id and the optional Demo_Override `today` field from the request, SHALL ignore every other submitted field (including any supplier id, amount, text or phone number), SHALL take the supplier id only from `session.supplierId`, SHALL resolve Today as the Debtor_Page does (the Demo_Override applies only to the demo supplier), and SHALL send only a Sendable_Draft.
2. IF the Draft id is not a uuid, matches no Draft, or belongs to an invoice of another supplier, THEN THE send server actions SHALL respond as not found in the same way for all three cases, make no Razorpay or Twilio call, and write no Message_Row, Escalation_Event or Pay_Link.
3. IF the Draft is not `approved`, or its step is not `whatsapp_nudge` or `whatsapp_paylink`, or it already has a Sent_Message, THEN THE send server actions SHALL make no Razorpay or Twilio call, write no Message_Row, Escalation_Event or Pay_Link, leave the Draft unchanged, and show "This draft can't be sent" as a failure result (`role="alert"`).
4. WHEN the owner sends a Sendable_Draft whose Approval_Day equals Today, THE send server actions SHALL run the Send_Check for Today before any Razorpay or Twilio call, and SHALL write one Tool_Log row with `tool` `next_escalation_step`, the invoice id, the Send_Check inputs and the Decision, whether or not the Send_Check passes.
5. IF the Send_Check does not pass (for example a promise was recorded after approval, or the invoice was paid), THEN THE send server actions SHALL make no Razorpay or Twilio call, write no Message_Row, Escalation_Event or Pay_Link, leave the Draft unchanged, and show "Not sent: <text>" as a failure result, where <text> is the Wait_Text of the Decision's reason when the Decision is `wait`, or the Step_Text of the Decision's step when the Decision is `advance` with a different step.
6. IF Today is not the Draft's Approval_Day, THEN THE send server actions SHALL make no Razorpay or Twilio call, run no Send_Check, write no Message_Row, Escalation_Event or Pay_Link, and show "This draft was approved on <Approval_Day as D MMM YYYY>. Approve a fresh draft to send today." (for example "12 Nov 2026") as a failure result, because the Draft's figures are as of its Approval_Day.
7. IF a session reaches a send server action with no `supplierId`, THEN THE action SHALL redirect to `/signin`, make no Razorpay or Twilio call, and write no row.
8. WHEN two or more send requests for the same Draft (Twilio send, "Open in WhatsApp", or one of each) arrive before any of them has finished, THE send server actions SHALL make at most one Twilio call, create at most one Pay_Link and write at most one Sent_Message for that Draft, and every other request SHALL show "This draft can't be sent" as a failure result. THE send server actions SHALL rely for this on the unique index on `payment_links.draft_id` (Requirement 3 criterion 3) and the partial unique index on `messages.draft_id` (Requirement 5 criterion 8): an insert rejected by either index SHALL end that request with "This draft can't be sent".
9. THE Approval_Queue approve action SHALL keep sending nothing (escalation-ladder Requirement 6 criterion 10); only the send controls of Requirement 4 trigger outbound messages.
10. IF a send server action is reached with a Stale_Session, THEN THE action SHALL end the Auth.js session, redirect to `/signin?error=SessionExpired` as dashboard-ui does, make no Razorpay or Twilio call, write no row, and SHALL NOT respond with HTTP 500.

### Requirement 3: Pay link and Outbound_Text

**User Story:** As a supplier, I want the message to carry a payment link for the exact invoice amount, so that the buyer can pay in one tap.

#### Acceptance Criteria

1. WHEN a Sendable_Draft passes the Send_Check, no Pay_Link is stored for that Draft and the Razorpay_Link_Lookup of criterion 9 finds no link, THE send server actions SHALL make exactly one Razorpay Payment Links API create call with `amount` = Pay_Amount in integer paise, `currency` `INR`, `accept_partial` false, `reference_id` = the Draft id, `notes` holding the invoice id, and `notify` with `sms` false and `email` false, so that Razorpay itself sends nothing to the buyer.
2. WHEN a Pay_Link already exists for the Draft (for example after a failed Twilio send or a rejected over-length Outbound_Text), THE send server actions SHALL reuse the stored Pay_Link URL and Pay_Amount and SHALL make zero Razorpay create calls.
3. WHEN the Razorpay create call succeeds or the Razorpay_Link_Lookup of criterion 9 finds a link, THE send server actions SHALL store exactly one `payment_links` row for the Draft, before any Message_Channel call. The row SHALL hold the Razorpay link id, the URL, Pay_Amount, status `created`, the Draft id in a new `draft_id` column and Today in a new `created_on` column. Both columns and a unique index on `payment_links.draft_id` SHALL be added through a Drizzle migration.
4. IF `RAZORPAY_KEY_ID` or `RAZORPAY_KEY_SECRET` is unset or empty, or `RAZORPAY_KEY_ID` does not start with `rzp_test_`, THEN THE send server actions for both "Send pay link" and "Open in WhatsApp" SHALL make zero Razorpay calls and zero Twilio calls, SHALL store no `payment_links` row, no Message_Row and no Escalation_Event, SHALL leave the Draft status `approved`, and SHALL show "Payments are not configured", so that only test mode is used.
5. IF the Razorpay_Link_Lookup or the Razorpay create call fails (an error response other than the HTTP 400 "reference ID already attempted" of criterion 9, a network error, or no response within 10 seconds), or the Razorpay_Link_Lookup after that HTTP 400 finds no link, THEN THE send server actions SHALL store no `payment_links` row, make zero Twilio calls, store no Sent_Message, leave the Draft status `approved`, and show an error message saying the payment link could not be created. The send control SHALL stay usable so the owner can retry.
6. THE send server actions SHALL build the Outbound_Text only from the Draft's stored `body_text`, the Draft's stored `rule_ids` and the Pay_Link URL: the Pay_Link_Marker SHALL be replaced by the Pay_Link URL only, and only a body with no Pay_Link_Marker SHALL get a blank line and the Pay_Link_Line appended. The Disclaimer SHALL be the last line. They SHALL format the Pay_Amount only with the Engine `formatINR`.
7. FOR ALL Sendable_Drafts, the Outbound_Text SHALL contain the Draft's `body_text` with only the Pay_Link_Marker replaced by the Pay_Link URL (or, when the body has no Pay_Link_Marker, the unchanged body followed by a blank line and the Pay_Link_Line), exactly one Pay_Link URL, zero occurrences of the Pay_Link_Marker, the Basis_Line built from the Draft's `rule_ids`, and the Disclaimer as its last line (invariant).
8. IF the Outbound_Text is longer than 1,600 characters, THEN THE send server actions SHALL make zero Twilio calls, store no Sent_Message, keep the stored Pay_Link, leave the Draft status `approved`, and show "Message too long for WhatsApp (max 1,600 characters)". THE WaMe_Link SHALL remain available. An Outbound_Text of exactly 1,600 characters SHALL count as within the limit.
9. WHEN no Pay_Link is stored for a Sendable_Draft, THE send server actions SHALL run the Razorpay_Link_Lookup before any Razorpay create call, and run it again when a create call returns HTTP 400 "reference ID already attempted".
10. IF the Razorpay_Link_Lookup of criterion 9 finds a link, THEN THE send server actions SHALL store that link as the Draft's `payment_links` row (criterion 3) and reuse it, with no further Razorpay create call.

### Requirement 4: Send controls on the Debtor_Page

**User Story:** As a supplier, I want to send the approved message from the buyer's page, with a fallback that uses my own phone, so that the demo works even if the sandbox fails.

#### Acceptance Criteria

1. WHILE an Invoice_Panel's invoice has a Sendable_Draft, the Buyer_Number is set and `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` and `TWILIO_WHATSAPP_FROM` are all set, THE Invoice_Panel SHALL show "Send pay link" as an enabled `<button>` that submits the Twilio send action for that Draft. Above the button, THE Invoice_Panel SHALL show a preview of the Outbound_Text with the Basis_Line and the Disclaimer as its last line. In the preview, the Pay_Link URL SHALL be shown as "<link created on send>": in place of the Pay_Link_Marker when the body has one, and otherwise in the appended line "Pay <formatINR(Pay_Amount)> here: <link created on send>". IF the invoice has more than one Sendable_Draft, THEN the controls SHALL act on the one whose Approved_Step_Event has the latest Approval_Day, with ties going to the latest-created Draft.
2. WHILE an Invoice_Panel's invoice has a Sendable_Draft, THE Invoice_Panel SHALL show "Open in WhatsApp" as an enabled `<button>` next to "Send pay link". The button SHALL run the same checks as Requirement 2 and Requirement 3 criterion 4. Only if every check passes SHALL it create or reuse the Pay_Link, write the Message_Row and Escalation_Event of Requirement 5 criterion 2, and open the WaMe_Link URL in a new browser tab. IF any check fails, THEN it SHALL open no URL, write no Message_Row, and show that check's message as the failure of criterion 6.
3. IF an Invoice_Panel's invoice has no Sendable_Draft, THEN THE Invoice_Panel SHALL show "Send pay link" with the HTML `disabled` attribute and the text "Approve a WhatsApp draft first", linked through `aria-describedby`. It SHALL show no "Open in WhatsApp" control and no Outbound_Text preview. This state SHALL take precedence over criteria 4 and 5.
4. IF the invoice has a Sendable_Draft and the Buyer_Number is null, THEN THE Invoice_Panel SHALL show "Send pay link" with the HTML `disabled` attribute and the text "No WhatsApp number for this buyer", linked through `aria-describedby`. "Open in WhatsApp" SHALL open `https://wa.me/?text=<URL-encoded Outbound_Text>`, so the owner picks the contact. This state SHALL take precedence over criterion 5.
5. IF the invoice has a Sendable_Draft, the Buyer_Number is set, and any of `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` or `TWILIO_WHATSAPP_FROM` is unset (including a `TWILIO_WHATSAPP_FROM` that does not match `^\+[1-9][0-9]{7,14}$`, Requirement 8 criterion 4), THEN THE Invoice_Panel SHALL show "Send pay link" with the HTML `disabled` attribute and the text "WhatsApp sender not configured", linked through `aria-describedby`. "Open in WhatsApp" SHALL stay enabled.
6. WHEN a send action returns, THE Invoice_Panel of that invoice SHALL show exactly one result message:
   - after a Twilio sent result: "Queued with Twilio. Delivery is not tracked." with `role="status"`;
   - after a WaMe_Link handoff: "Opened in WhatsApp. Tap Send on your phone." with `role="status"`;
   - after any failure: the failure message from Requirement 1 criteria 3 and 7, Requirement 2 criteria 2 to 8, Requirement 3 criteria 4, 5 and 8, or Requirement 5 criteria 7 and 8, with `role="alert"`, with no Sent_Message written, and with the Draft still a Sendable_Draft.
7. WHEN an invoice has a Sent_Message, THE Invoice_Panel SHALL show its latest Sent_Message as "Sent on <D MMM YYYY> via <Twilio sandbox | your WhatsApp>". The date SHALL be the `occurred_on` of the matching `sent` Escalation_Event. Because that Draft is no longer a Sendable_Draft, the controls SHALL then follow criterion 3.
8. WHILE a send action for an Invoice_Panel is in progress, THE Invoice_Panel SHALL disable both "Send pay link" and "Open in WhatsApp", so that one click submits at most one request.
9. THE "Start call" Placeholder_Button SHALL stay disabled with "Arrives with voice call", and THE Graveyard_Page SHALL stay unchanged except for the resurrected state of Requirement 6.
10. THE send controls SHALL keep the Debtor_Page theme and accessibility rules of debtor-ui Requirement 9: real buttons, targets at least 44 × 44 CSS px, and WCAG 2.2 AA contrast, including disabled text.

### Requirement 5: Records of a send

**User Story:** As a supplier, I want every send on the timeline, so that I can see what my buyer received and when.

#### Acceptance Criteria

1. WHEN the Twilio_Sandbox returns a sent result, THE send server actions SHALL write, in one transaction, exactly one Message_Row (channel `twilio_sandbox`, direction `outbound`, the Outbound_Text, status `sent`, the Draft id, `provider_message_id` = the Twilio message SID, `error_code` null) and exactly one Escalation_Event with `action` `sent`, the Draft's id and step, `occurred_on` = Today (the Demo_Override `today` for the demo supplier) and `detail` `{ channel: "twilio_sandbox", messageRowId }`, where `messageRowId` is the id of that Message_Row.
2. WHEN the owner clicks "Open in WhatsApp" on a Sendable_Draft and the Requirement 2 checks pass, THE send server actions SHALL write, in one transaction and before returning the WaMe_Link URL, exactly one Message_Row (channel `wa_me`, direction `outbound`, the Outbound_Text, status `handed_off`, the Draft id, `provider_message_id` null, `error_code` null) and exactly one Escalation_Event with `action` `sent`, the Draft's id and step, `occurred_on` = Today and `detail` `{ channel: "wa_me", messageRowId }`.
3. IF the Twilio_Sandbox returns a failure, THEN THE send server actions SHALL write exactly one Message_Row per failed attempt (channel `twilio_sandbox`, direction `outbound`, the Outbound_Text, status `failed`, the Draft id, `provider_message_id` = the Twilio message SID when the create call returned one (a failure reported by a status poll) and null otherwise, `error_code` = the provider error code), SHALL write no Escalation_Event, SHALL keep the stored Pay_Link, and SHALL leave the Draft a Sendable_Draft so that the owner can retry or use "Open in WhatsApp".
4. THE `packages/db` schema SHALL add `sent` to the `escalation_action` enum through a Drizzle migration that keeps every existing enum value and row, and THE debtor-ui Action_Text map SHALL map `sent` to "sent", so that the Candle_Timeline shows one entry "<Step_Text> sent" (for example "WhatsApp nudge sent") on the event's `occurred_on` date for each `sent` Escalation_Event.
5. THE Ladder_Runner, the Approval_Queue and the Send_Check SHALL build the Engine_History from Approved_Step_Events only, so that for any invoice the `nextEscalationStep` Decision is the same with or without its `sent` Escalation_Events.
6. THE send server actions SHALL write exactly one Tool_Log row per Razorpay_Link_Lookup (`tool` `find_payment_link`), exactly one per Razorpay create call (`tool` `create_payment_link`) and exactly one per Message_Channel call, whether it returns a sent, handoff or failure result (`tool` `send_whatsapp`). Each row SHALL hold the invoice id, inputs and outputs. No field of the row SHALL contain the full Buyer_Number, the WaMe_Link URL included: only its last four digits may appear. No field SHALL contain an API key, auth token or secret. A reused Pay_Link writes no `create_payment_link` row; a Pay_Link already stored for the Draft also writes no `find_payment_link` row.
7. IF the transaction of criterion 1 or 2 fails, THEN THE send server actions SHALL roll back both the Message_Row and the Escalation_Event, SHALL show the failure with `role="alert"` and not the success status of Requirement 4 criterion 6, and SHALL keep the `send_whatsapp` Tool_Log row with the Twilio message SID when one was returned.
8. THE `packages/db` schema SHALL add the Message_Row columns `draft_id`, `provider_message_id` and `error_code` and a partial unique index on `messages.draft_id` WHERE `status` IN (`'sent'`, `'handed_off'`) through a Drizzle migration, and IF a Sent_Message insert is rejected by that index, THEN THE send server actions SHALL roll back the transaction of criterion 1 or 2 and show "This draft can't be sent" with `role="alert"`.

### Requirement 6: Razorpay payment webhook resurrects the tombstone

**User Story:** As a supplier, I want the invoice marked paid as soon as the buyer pays the link, so that the tombstone resurrects without my doing anything.

#### Acceptance Criteria

1. IF `RAZORPAY_WEBHOOK_SECRET` is unset or empty, THEN THE Razorpay_Webhook SHALL respond with HTTP 503, write no Webhook_Event_Table row, no Tool_Log row and no Pay_Link or invoice change.
2. IF the `X-Razorpay-Signature` header is missing or does not equal the hex HMAC-SHA256 of the raw request body keyed with `RAZORPAY_WEBHOOK_SECRET` (compared in constant time), THEN THE Razorpay_Webhook SHALL respond with HTTP 401 and write no Webhook_Event_Table row, no Tool_Log row and no Pay_Link or invoice change.
3. WHEN a signature-verified `payment_link.paid` event arrives whose payment link id (`payload.payment_link.entity.id`) matches a stored Pay_Link and whose paid amount in paise (`payload.payment_link.entity.amount_paid`) equals that Pay_Link's Pay_Amount, THE Razorpay_Webhook SHALL, in one database transaction, set the Pay_Link status to `paid`, set the invoice `paid_on` to the Payment_Day if `paid_on` is null, record the (`razorpay`, event id) pair in the Webhook_Event_Table, and then respond with HTTP 200.
4. IF a verified event's `x-razorpay-event-id` is already in the Webhook_Event_Table for provider `razorpay`, including when two deliveries of the same event id arrive at the same time, THEN THE Razorpay_Webhook SHALL respond with HTTP 200 to each delivery, apply the criterion 3 changes at most once in total, and change no Pay_Link or invoice for the repeat delivery.
5. IF a verified event is not `payment_link.paid`, names a payment link id (`payload.payment_link.entity.id`) that matches no stored Pay_Link, or has a paid amount in paise (`payload.payment_link.entity.amount_paid`) different from the Pay_Amount, THEN THE Razorpay_Webhook SHALL record the event id in the Webhook_Event_Table, change no Pay_Link and no invoice, and respond with HTTP 200. The Tool_Log row for the event is written by criterion 8.
6. IF a verified `payment_link.paid` event matches a stored Pay_Link and its Pay_Amount but the invoice already has a non-null `paid_on`, THEN THE Razorpay_Webhook SHALL keep the existing `paid_on` unchanged, set the Pay_Link status to `paid`, record the event id in the Webhook_Event_Table in the same transaction, and respond with HTTP 200.
7. WHEN the Razorpay_Webhook commits a change to an invoice's `paid_on`, THE `apps/web` app SHALL revalidate `/` and `/debtors/<Buyer_Id>` before the HTTP 200 response, so that the next load of either page with Today on or after the Payment_Day shows Tombstone_State `resurrected` and a Candle_Timeline entry "Paid. Resurrected".
8. THE Razorpay_Webhook SHALL write exactly one Tool_Log row with `tool` `razorpay_webhook` per signature-verified delivery, holding the event id, event type, Pay_Link id (null if unknown), paid amount in paise and exactly one outcome from `paid`, `already_paid`, `duplicate`, `ignored_event_type`, `unknown_link`, `amount_mismatch` or `invalid_payload`, and SHALL include no stack trace, SQL text or secret in any response body.
9. IF a signature-verified request has a body that is not valid JSON, or has no `x-razorpay-event-id` header, THEN THE Razorpay_Webhook SHALL respond with HTTP 400, write no Webhook_Event_Table row, and change no Pay_Link or invoice.
10. IF the database transaction of criterion 3 or 6 fails, THEN THE Razorpay_Webhook SHALL roll back every change from that transaction, including the Webhook_Event_Table row, and respond with HTTP 500 with no error detail in the body, so that Razorpay's retry of the same event id is processed as a new delivery.
11. WHEN a request reaches the Razorpay_Webhook, THE Razorpay_Webhook SHALL read the raw body with `req.text()` before any JSON parsing, and SHALL compute the signature of criterion 2 over that raw text.

### Requirement 7: Twilio inbound webhook (log only)

**User Story:** As a supplier, I want buyer replies kept, so that I can read them later, without the agent acting on them.

#### Acceptance Criteria

1. IF `TWILIO_AUTH_TOKEN` or `PUBLIC_BASE_URL` is unset or empty, THEN THE Twilio_Webhook SHALL respond with HTTP 503, write no Tool_Log row and write no Webhook_Event_Table row.
2. IF the `X-Twilio-Signature` header is missing, or the official `twilio` package's `validateRequest(TWILIO_AUTH_TOKEN, <X-Twilio-Signature header>, <url>, <POST form parameters>)` returns false, where `<url>` is `PUBLIC_BASE_URL` with any trailing slash stripped followed by `/api/webhooks/twilio`, THEN THE Twilio_Webhook SHALL respond with HTTP 401, write no Tool_Log row and write no Webhook_Event_Table row.
3. WHEN a signature-verified inbound message with a `MessageSid` not yet in the Webhook_Event_Table arrives, THE Twilio_Webhook SHALL, in one atomic write, record the `MessageSid` in the Webhook_Event_Table with provider `twilio` and write one Tool_Log row with `tool` `whatsapp_inbound`, the `MessageSid`, the sender number with every character except its last four digits masked, and the first 1,600 characters of `Body` stored as untrusted data. It SHALL then respond with HTTP 200 and an empty TwiML `<Response/>`.
4. THE Twilio_Webhook SHALL send no reply message, change no invoice, Draft, promise or Escalation_Event, make no LLM call, and never interpret the `Body` as an instruction.
5. IF a verified `MessageSid` is already in the Webhook_Event_Table (including two concurrent deliveries of the same `MessageSid`), THEN THE Twilio_Webhook SHALL respond with HTTP 200 and an empty TwiML `<Response/>` and write no second Tool_Log row or Webhook_Event_Table row.
6. IF a signature-verified request has no `MessageSid` or an empty one, THEN THE Twilio_Webhook SHALL respond with HTTP 400, write no Tool_Log row and write no Webhook_Event_Table row.
7. IF the database write in criterion 3 fails, THEN THE Twilio_Webhook SHALL roll back so that neither the Webhook_Event_Table row nor the Tool_Log row persists, respond with HTTP 500, and include no stack trace, SQL text, auth token or unmasked sender number in the response. A later Twilio retry of the same `MessageSid` is then handled as a first delivery.

### Requirement 8: Secrets and configuration

**User Story:** As a developer, I want every key in env vars and nothing live by accident, so that the demo is safe to run.

#### Acceptance Criteria

1. THE `apps/web` app SHALL read every Channel_Env value only from server-side environment variables at request time, and `apps/web/.env.example` SHALL list every Channel_Env name, both required and optional (including `DEMO_BUYER_WHATSAPP`), each with an empty value and no other content on its line.
2. THE `apps/web` app SHALL NOT include the value of `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `RAZORPAY_KEY_SECRET` or `RAZORPAY_WEBHOOK_SECRET` in any HTTP response body, rendered page HTML, client-side JavaScript, Tool_Log row, Message_Row or error message shown to the user.
3. THE git-tracked files of the repository SHALL contain no Twilio Account SID or auth token, no Razorpay key id, key secret or webhook secret, no value from a developer's local env file, and no real phone number. Any phone number in a test or fixture SHALL be a fictional placeholder, and every local env file other than `apps/web/.env.example` SHALL be git-ignored.
4. IF a required Channel_Env value is unset or set to an empty string, or `TWILIO_WHATSAPP_FROM` does not match `^\+[1-9][0-9]{7,14}$` (for example a value with the `whatsapp:` prefix), THEN THE `apps/web` app SHALL treat it as unset and SHALL disable the dependent control or route as follows: an unset Twilio value disables "Send pay link" (Requirement 4 criterion 5); an unset `RAZORPAY_KEY_ID` or `RAZORPAY_KEY_SECRET` makes both send controls show "Payments are not configured" (Requirement 3 criterion 4); an unset `RAZORPAY_WEBHOOK_SECRET` makes the Razorpay_Webhook respond with HTTP 503 (Requirement 6 criterion 1); an unset `TWILIO_AUTH_TOKEN` or `PUBLIC_BASE_URL` makes the Twilio_Webhook respond with HTTP 503 (Requirement 7 criterion 1). THE `apps/web` app SHALL NOT respond with HTTP 500 in any of these cases.
5. WHILE every Channel_Env value is unset, THE `apps/web` app SHALL build, and THE Graveyard_Page and Debtor_Page SHALL render for the Demo_Seed without HTTP 500, with "Send pay link" in one of the disabled states of Requirement 4 criteria 3 to 5.
6. THE Razorpay_Webhook and the Twilio_Webhook SHALL each run on the Node.js runtime (`export const runtime = "nodejs"`).
7. THE `config.matcher` of `apps/web/proxy.ts` SHALL match no path under `/api/webhooks/`, so that the Auth.js proxy never intercepts the Razorpay_Webhook or the Twilio_Webhook.
